gRPC-Based Distributed File System

A distributed file system extending an RPC service with synchronization and concurrency control.

C++ · gRPC

Purpose

Build a distributed file system (DFS), similar to the Andrew File System approach, by extending an underlying RPC layer with synchronization and concurrency control across multiple clients.

Design

The design adds synchronization logic on top of four core RPC operations — Fetch, Store, List, and Delete. The goal is to keep multiple clients consistent with the server while preventing two clients from modifying the same file at the same time.

The server is treated as the main source of truth. Clients compare their local files against the server's file list and metadata, then decide whether a file needs to be fetched, stored, deleted, or left unchanged.

Concurrency is handled with a write-lock system (std::map<file_name, client_id> write_locks and an RPC Lock() method) on the server. Before a client can store or delete a file, it must acquire the lock for that file. The server tracks which client owns each lock and rejects write operations from clients that do not hold the correct lock.

For synchronization updates, a callback/watcher mechanism is used. When the server detects that files have changed, it signals waiting callback requests so clients can refresh their local version of the affected files. CRC checksums and modification times are used to compare file versions, avoiding unnecessary transfers when client and server already agree.

Design Choice Function Why
Write-lock system Allows only one client to modify a file at a time Prevents concurrent writes and keeps file contents consistent
Mutex + RAII (std::lock_guard) Protects shared data structures from concurrent thread access Avoids errors from manual locking
Condition variable for callbacks Blocks and wakes threads when updates occur Avoids busy-waiting with a straightforward implementation
CRC checksums Detects differences in file contents Easy to use and sufficient for project requirements
Modification times Tracks file updates for synchronization decisions Accurate and low overhead

Service Interface

The protobuf service definition exposed by the server:

service DFSService {
  // Store files on the server (streaming upload)
  rpc Store(stream StoreRequest) returns (StoreResponse);

  // Fetch files from the server (streaming download)
  rpc Fetch(FetchRequest) returns (stream FetchResponse);

  // List all files on the server
  rpc List(ListRequest) returns (ListResponse);

  // Get the status of a single file
  rpc Stat(StatRequest) returns (StatResponse);

  // Request a write lock from the server
  rpc Lock(LockRequest) returns (LockResponse);

  // Asynchronous file listing with attribute info (name, size, mtime)
  rpc CallbackList(CallbackListRequest) returns (CallbackListResponse);

  // Delete a file from the server
  rpc Delete(DeleteRequest) returns (DeleteResponse);
}
